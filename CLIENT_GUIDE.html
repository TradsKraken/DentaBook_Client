Project guide

Purpose

DentaBook helps people browse approved clinics, explore treatments, estimate published costs, and request appointments. The source in this delivery matches the production features released through 8 November 2026. Clinic review, direct GCash verification, unpaid Pay at clinic confirmation, cancellation/rescheduling, private intake/follow-up, profile/password editing, and scoped staff access are live.

Who uses the website

PersonAvailable behavior
VisitorBrowse clinics, public profiles, treatments, and estimates without signing in
PatientRegister/sign in, request and track own appointments, manage eligible changes/payments, submit intake/replies, and edit name/phone/password
Clinic ownerRegister/check approval; manage setup, appointments, intake, hours, payments, staff invitations, and access
Clinic managerManage clinic setup, appointments, intake, hours, and payments; cannot manage staff access
Appointment staffHandle appointments, private intake/follow-up, and working hours; cannot administer payments or edit clinic/service/dentist setup
Platform administratorReview clinic submissions on the separate administration website

The server validates roles, approval, membership, and record ownership. Public registration cannot grant administrator access. Dentist profiles do not create sign-in accounts. Clinics appear publicly only after approval, and listings use saved records with honest loading/empty/error states.

Delivery boundaries

The calculator estimates published costs without creating a booking or collecting money. New requests reserve available times and retain quoted treatments/prices. Clinics accept/decline requests before patients choose explicitly enabled payment methods. GCash references require actual clinic verification; Pay at clinic remains unpaid. Cancellation/rescheduling follow clinic-configured rules and preserve payments/receipts.

Clinics supply their own intake questions and purpose/retention statements. Answers remain private to the patient and authorized clinic staff; follow-up appears in the signed-in portals. Retention statements do not trigger automatic record deletion. Owners share staff invitations directly, without automated email delivery.

Email/SMS/push and automated reminders, password recovery, verified email changes, closures/buffers, reservation expiry, public reviews/moderation, cash collection/refund recording, MFA, complete appointment/payment history pagination, and expanded off-host recovery remain planned. Clinic concerns, in-app notifications, dentist access, completion and private feedback are live. See the status and development plan.

Interface and handoff

The supplied DentaBook branding and blue-and-white theme are retained. Layouts begin on phones, with stacked forms, readable controls, touch targets, and contained scrolling regions. No clinics, ratings, credentials, prices, or appointment records are invented.

This handoff contains source, migrations, configuration templates, automated tests, asset notices, and client documentation. Live data, private credentials, backups, and hosting access are excluded. See the user guide for available tasks.

User guide

Current through the live release of 8 November 2026.

For a visual walkthrough, see the patient, clinic, and administrator workflows.

Browsing without an account

  1. Open https://dentabook.forgroup.space.
  2. Choose Find a clinic to open the directory.
  3. Search by the clinic, service, dentist, or location information available in the saved records.
  4. Open a clinic to view its public contact details, active services, and active dentist information.
  5. Use Cost calculator to select a clinic and its published treatments.
  6. Contact the clinic to confirm suitability, availability, and the final price.

If no clinics are listed, approved records have not been published yet. If an error message appears, use the retry action. An empty directory is not the same as a connection error.

Creating a patient account

  1. Open Patient registration at /patient/register.
  2. Enter your name, email address, phone number, and password.
  3. Confirm the same password and submit the form.
  4. After the account-ready message, continue to patient sign-in.
  5. Sign in with the email address and password you registered.

Passwords must contain at least 12 characters and no more than 72 UTF-8 bytes. Some symbols use more than one byte; an ordinary longer passphrase can meet the minimum without using complex symbols.

Patient registration does not grant clinic or administrator access. Password recovery and email verification are not yet implemented. If you forget your password, contact the designated website operator; there is no self-service reset link in this release.

Using patient pages

My account shows the signed-in patient's saved information. My appointments shows appointments already associated with that account, or an empty message when none exist. Other patients' information is not available through these pages.

Opening a personal page while signed out leads to patient sign-in. After a successful sign-in, the website returns to the requested patient page. To request a visit:

  1. Open Book an appointment or a clinic’s Request an appointment link.
  2. Select a clinic, treatment, assigned dentist, and date.
  3. Choose an available time and check the estimated cost. Your account email is filled when available; you may enter a different appointment contact email without changing your account email or appointment ownership. Check your phone number and add optional visit notes.
  4. Answer the clinic’s applicable intake questions and explicitly agree to share your answers. Required answers and booking save together; refresh options if the questions changed. Submit once and read the saved request code. The initial status is pending review.
  5. Open My appointments and use Refresh appointments to see the clinic’s decision and note.

Accounts without an email can enter a valid appointment contact email. An appointment contact email never grants access to the account.

All times use Philippine time. Requests cover one treatment, today through 90 days ahead, with 15 minutes of lead time. If a time or quote changes, refresh and choose from the current options. A saved pending request reserves the time while the clinic reviews it. Identical submission retries return the same saved request.

Accepted means the clinic accepted the request. Open Deposit & payment details to see the clinic’s enabled GCash and Pay at clinic options. GCash requires agreeing to the saved deposit/refund terms, transferring in your own GCash app to the displayed clinic account, then submitting the transaction reference. Never provide your PIN or OTP. Staff check their actual account before verifying payment; an eligible accepted visit is then confirmed and a deposit receipt is available to you. Pay at clinic requires staff confirmation and remains unpaid without a receipt. If no method is enabled, contact the clinic. A declined request shows the clinic’s reason. Use Manage appointment for cancellation or reschedule requests when enabled by the clinic. The clinic sets notice deadlines and terms; the original reservation remains until a requested replacement is approved. Cancellation preserves payments/receipts and may require refund review; it does not return money automatically.

Registering a clinic

  1. Open /clinic/register on the main website.
  2. Enter the authorized account holder's name, account email, and password.
  3. Enter the clinic's name, address, public phone, public email, and registration or license reference.
  4. Confirm that you are authorized to register and manage the clinic.
  5. Submit the registration.
  6. Sign in at /clinic/sign-in to check the result.

The account email is used for sign-in. The public clinic email is contact information intended for the clinic's public listing. Submitting a registration does not automatically publish the clinic or approve its credentials.

For owners and managers, the approved-clinic workspace opens on Overview, showing pending requests, published service/dentist counts, and a four-step booking setup checklist. Use the sidebar on a desktop or the clinic navigation menu on a phone. Each section has its own page and supports refresh/back navigation.

The workspace provides these tools:

  1. Clinic profile: save the public name, description, address, phone, and contact email. Account sign-in email remains separate.
  2. Services & prices: search or filter the saved service list. Choose Add a service or Edit service to open a focused form panel for categories, descriptions, estimated PHP prices, durations, and publication. Unpublish a service to hide it while retaining its details/history.
  3. Dentists: search/filter the team list, then choose Add a dentist or Edit dentist. In the panel, edit accurate details, publication, and assigned treatments. A profile does not create a staff account.
  4. Working hours: view shifts grouped by weekday or filter them by dentist. Choose Add working hours, choose one or more published dentists and days (or use Monday–Friday/Every day), enter shifts, check the preview, then Save working hours. Choose Add split shift for a lunch break or other gap. Use Edit hours on a saved shift to change its day/times. The whole batch is rejected if any shift overlaps; identical saved shifts are kept on retry. Hours recur in Philippine time. Existing appointments retain their saved times after hours change.
  5. Appointments: search loaded requests, choose a status, or refresh the inbox. Choose Review request to open the patient/visit details, then Accept request or Decline request and confirm your decision. Declining requires a reason the patient can read. Reviewed records have View details. An accepted request proceeds to the clinic’s enabled payment choices. Use Deposits & payments to review submitted references or Pay at clinic requests.

Editor and review panels keep the current list in context. Close panel, Cancel editing, or Escape dismisses an idle panel. A failed save keeps the entered fields so you can correct or retry it.

Keep the inbox current: pending requests reserve the dentist’s time until reviewed and do not expire automatically. Acceptance rechecks current assignments, working hours, publication, and conflicts. Existing decisions cannot be overwritten through the pending-request review action. The current administrator interface approves or rejects pending clinics; it does not provide a complete suspension-management workflow.

Deposits & payments

Enable only the methods your clinic accepts. For GCash, save your actual account name and 11-digit mobile number, an explicit deposit percentage, and cancellation/refund terms. Pay at clinic may be enabled without a deposit percentage. Existing GCash choices retain their saved amount, terms, and recipient when settings change.

In payment records, choose Review payment choice. For GCash, open your clinic’s actual GCash transaction history, match the incoming reference and exact amount, then enter both and acknowledge the account check. A patient-submitted reference is only a claim. Verification records the reviewer/time and creates a deposit receipt; future accepted visits are confirmed. Payments verified after a visit becomes unavailable are recorded for follow-up without confirming the visit. Rejecting a choice requires a patient-visible reason. Verified references cannot be reused.

For Pay at clinic, confirm the visit while leaving payment unpaid. No cash payment or receipt is invented. Cash collection recording and automatic refunds are future work. Receipts are payment acknowledgements, not tax invoices.

Patient profile and private intake

On My account, edit your full name/phone and choose Save profile. Saved appointments keep their original contact details. To change your password, supply the current password, enter/confirm the new password, and save; all devices are signed out. Account-email changes remain unavailable until verified email delivery is implemented.

On My appointments, open Intake & clinic follow-up. If the clinic enabled questions for this treatment, read its purpose/retention statements, answer required/optional questions, agree to share, and choose Save intake answers. Saved versions retain the original questions. If the clinic requests information, enter Your response and choose Send response. Check the portal for updates; email/SMS messages are not yet sent. Closed visits retain their saved information but do not accept new answers or requests.

Clinic intake and staff access

Owners/managers open Patient intake to add questions, choose written or yes/no/unsure answers, make an answer required, and apply a question to all treatments or one saved clinic service. Enter the collection purpose and your actual record-retention policy before enabling intake. Saving a policy does not schedule record deletion. In Appointment inbox → View details, authorized staff read submissions and use Request information from patient; the request and patient's reply retain their authors/times without changing visit or payment status.

Only owners use Staff access. Enter a staff email, choose Manager or Appointment staff, and create an invitation. Copy the private link and share it directly with that person; it is shown once and expires after 48 hours. Replacing an invitation invalidates the earlier link. A new staff member enters their name and chooses a password; an existing clinic-staff account uses its invited email and existing password. Patient/admin identities cannot be converted into staff accounts.

Owners can change roles, revoke unused invitations, remove active access, and review access history. Revocation invalidates clinic sessions immediately. Managers manage setup, intake, appointments, hours, and payments but cannot grant staff access. Appointment staff handle appointments/intake/follow-up and working hours; other setup/payment tools remain restricted. Dentist profiles alone never grant sign-in access. Dentist-specific sign-in and MFA remain planned.

Reviewing clinics as an administrator

  1. Open https://dentabook-admin.forgroup.space/admin/sign-in.
  2. Sign in with an administrator account provided through the operator setup process.
  3. Open the list of pending clinic registrations.
  4. Review the submitted details and reference information using the organization's review procedure.
  5. Choose approve or reject and complete the confirmation step.
  6. Provide a reason when rejecting a registration.
  7. Confirm that the updated result appears in the appropriate list.

A review records the decision, reviewer, time, and notes. Approval is an application publishing decision; the software does not independently verify a professional license. There is no public administrator registration or default administrator password.

Signing out and switching accounts

Choose Sign out before using a shared device or changing between patient and clinic accounts. Those two roles share the main website's browser session. Administrator access has its own hostname and session. Administrator sessions last one hour; patient and clinic sessions last eight hours unless revoked earlier.

If sign-in expires, sign in again. Changing a password or account role through an authorized maintenance process revokes existing sessions.

Ask your chosen clinic before booking

Open a clinic profile and choose Ask about a concern, or open My clinic concerns. Sign in, choose the clinic, and describe your symptoms and reason for a check-up (10–4,000 characters). Only this clinic receives it. One open concern is allowed per clinic; another draft moves to the existing conversation’s reply field. Up to three new concerns are allowed in 24 hours and five messages per minute per author.

An active owner-invited dentist opens Patient concerns, reads an unassigned conversation and selects Accommodate patient. Only the first successful claim assigns the dentist. The patient sees the assigned dentist’s name. Dentists see their own assigned concerns and the unassigned queue, while authorized clinic staff can triage concerns. Owners/managers may reassign to an active dentist with a reason. Replies and management history stay private to the patient and authorized clinic.

Staff can close, mark spam or reopen a concern. Owners/managers can impose a clinic-specific 24-hour restriction or remove it, with patient-visible reasons. These actions do not restrict appointment booking at other clinics. Accommodating a concern does not reserve a time or confirm an appointment; use Book an appointment with this clinic when ready.

Notification tabs

Patients use the header bell or Notifications link. Clinics and dentists use Notifications in the workspace menu. New concerns and patient replies notify the chosen clinic; clinic replies, assignment and management updates notify the patient. Notifications respect current access, refresh every 30 seconds while visible and on focus, and link to the related concern. Use Mark as read or Mark all as read; each person has their own saved read state. Previous/Next controls reach older notifications. Email/SMS, device push, and appointment reminders are not enabled.

Dentist access, completed visits and feedback

Owners choose Staff access, invite a Dentist, and link an active dentist profile from their clinic. The dentist accepts the private single-use invitation and signs in at /clinic/sign-in. A public profile alone grants no account access. Dentists review only assigned appointments and see their private intake/follow-up. They cannot manage staff, payments, clinic setup, or appointment changes. Removing access, hiding the profile or suspending the clinic removes access on subsequent requests.

After a confirmed visit’s scheduled end, authorized staff or the assigned dentist can confirm attendance and select Mark visit completed. Resolve pending appointment changes first. Completion records the staff member/time; it does not collect payment or change unpaid status. The patient then opens My appointments, chooses a rating (1–5), and submits optional feedback once. Feedback is private to the patient and authorized clinic staff; no public rating is published.

Showing or hiding a password

Passwords start hidden on sign-in, registration, clinic invitations and patient password changes. Tap the eye icon inside the field to reveal the characters, then tap the crossed-eye icon to conceal them. There is no separate text button. Each password/confirmation field is independent. The toggle can be used with keyboard Tab and Space/Enter and does not submit the form. It does not change the value, validation or account password, and visibility is not stored between visits.

Technical overview

How the website is organized

DentaBook has three application layers: the browser interface, the server API, and the database. Production runs the API in two processes so administrator access is separated from the public and clinic site.

How information moves through the system

When a visitor opens the clinic directory, the browser requests /api/clinics. The API reads approved clinics and their active public services and dentist information. It returns data for the interface to display. If the query fails, the page shows a loading error rather than an invented clinic listing.

When a patient or clinic representative signs in, the server checks the password hash and required role. It creates a random session token, stores only its hash, and places the token in a protected browser cookie. Each private request is checked against the saved session. Authentication uses database-backed opaque sessions; it does not use JWT tokens.

When an administrator reviews a registration, the administrator API checks the session and role before changing a pending clinic's status. The change is saved with the reviewer and review information. Public directory queries only include approved clinics.

Implementation approach

The application is organized into incremental capabilities: public discovery, account registration and permissions, clinic review, production separation, and testing. Interfaces use actual API data and explicit states for incomplete operations. Database changes are applied through versioned migration files rather than relying on manual changes to every installation.

The supplied source matches the live clinic management, assignments, slots, persistent requests, review/payment/change workflows, intake/follow-up, profile editing, scoped staff access, and batch hours. Booking/setup writes lock the clinic while validating and saving; request keys protect retries. Membership/approval checks enforce staff permissions. Additive migration 007 stores consented intake snapshots, follow-up, hashed invitations, memberships, and staff access events. The development plan records current rules and remaining work.

Setup and deployment

This guide is for the person responsible for hosting. Routine users only need a browser and the website addresses in the user guide.

Requirements

Use a server with Docker Engine and Docker Compose 2.24.4 or newer. Production requires the public and administrator hostnames to point to a reverse proxy, a valid certificate for each hostname, and HTTPS. Node.js 22 is needed on a workstation only when running development tools outside Docker.

Run a test installation on a separate machine from the live stack. The supplied container names are fixed; another copy on the same machine will conflict with the running containers unless the operator deliberately changes the configuration.

Local evaluation

  1. Copy .env.example to .env in the project root.
  2. Replace the database password placeholder with a newly generated random password.
  3. Set NODE_ENV=development and CLIENT_URL=http://localhost:3000.
  4. Keep the production COMPOSE_FILE setting disabled for a combined local preview.
  5. Confirm that ports 3000, 5000, and the chosen database diagnostic port are unused.
  6. Run:
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
curl --fail http://localhost:3000/api/health

Open http://localhost:3000. Local patient, clinic, and administrator routes share that origin, with server-enforced roles. Local HTTP is for controlled evaluation; production uses HTTPS.

First administrator

An operator creates the first real administrator interactively:

docker compose exec api npm run create-admin

Enter the intended person's name, email, and a private password. There are no default administrator credentials. Transfer access through the agreed private process, not through a source-code file or this documentation.

Verify the installation

curl --fail https://dentabook.forgroup.space/api/health
curl --fail https://dentabook-admin.forgroup.space/api/health
curl --fail --location --head https://dentabook-admin.forgroup.space/
curl --fail --head https://dentabook.forgroup.space/clinic/sign-in

Check public Internet access separately from LAN access: local DNS may bypass Cloudflare. The public patient and clinic pages should return 200 without a repeated redirect. The administrator root should make one redirect to its sign-in page, then return 200.

Both health responses should report healthy and a connected database. Administrator pages must return 404 on the public host; patient and clinic pages must return 404 on the administrator host. Then run the acceptance checks.

If the domains change, update the origins in .env, rebuild the client, recreate the API services, and update DNS/certificates. Public and clinic links are configured during the website build.

Operations manual

Routine checks

Use the correct project directory and production .env. Check docker compose ps, both HTTPS health endpoints, certificate renewal, available disk space, and the most recent verified backup. Agree an appropriate check schedule and responsible operator before relying on the system for daily operations.

docker compose ps
docker compose logs --tail=100 api admin_api client db

Logs can contain operational or account-related information. Share only the relevant, redacted excerpt when requesting support.

Backing up the database

The persistent Docker volume keeps records when containers are replaced. It is not a separate backup. Create a private backup before every release or database maintenance operation, and on the schedule agreed with the project owner.

From the project root on a Linux host:

mkdir -p .local/backups
chmod 700 .local/backups
umask 077
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > ".local/backups/dentabook-$(date +%Y%m%d-%H%M%S).sql"

Keep a protected copy outside the production server. Test recovery periodically in an isolated environment. Store the configuration and access needed for recovery separately from the database backup. This release does not configure scheduled backups, backup encryption, or retention automatically.

Recovery procedure

  1. Identify the last verified backup and the application version it belongs to.
  2. Prepare an isolated PostgreSQL 16 database with the required database role and extension permissions.
  3. Restore the SQL backup into a new, empty database using an authorized database operator's connection. A command such as psql --set ON_ERROR_STOP=1 --dbname "$RESTORE_DATABASE_URL" --file backup.sql must target that recovery database, not the live one.
  4. Check account and clinic record counts, session behavior, directory data, and the relevant application workflows against the restored database.
  5. Agree the production recovery window and data cutover before reconnecting the live application.
  6. Repeat the health and acceptance checks after cutover.

The backup format is plain SQL. Restoring it into an already initialized database may conflict with existing tables or records; prepare an empty recovery database and stop on errors. Do not attempt a production restore by trial and error.

Installing a new release

Confirm that the release has passed the agreed tests and read its release notes. Obtain and test the approved release using the agreed branch or tag, and commit the intended source. The release manager saves the current running images and a verified database backup before replacing services and retains the five newest saved versions. Then run:

python3 scripts/releases.py deploy --note "Describe the tested website feature or fix."
python3 scripts/releases.py list

Verify the two HTTPS health endpoints and the user journeys. Database migrations run at startup and may require a recovery plan beyond restarting an old image. The current project has no general automatic migration-down command.

Never use docker compose down -v for a routine update: it deletes the named database volume. docker compose down stops the stack without deleting that named volume. Keep production configuration independent from local testing.

Booking rules

All times use Asia/Manila. Patients can request today through 90 days ahead, with at least 15 minutes of lead time. Booking request contract (live)

POST /workspaces/patient/appointments accepts clinicId, serviceId, dentistId, date (YYYY-MM-DD), time (HH:MM), phone, notes (up to 2,000 characters), requestKey (UUID), expectedPrice (decimal string), and expectedDuration (integer minutes). Each request contains one treatment. The patient identity, stored price/duration, and initial pending_review status are assigned by the server. The request accepts a valid appointment contact email, prefilled from the account when available. Accounts without email enter the appointment address manually. This never changes the account email or grants account access. Existing identical retries retain the originally saved email. A changed quote or unavailable time returns 409.

Generate a new request key for a new request and reuse it for an identical retry. A saved identical retry returns HTTP 200 with the same appointment; initial creation returns 201. Reusing a key with changed details returns 409. The response includes appointment with its code, status, visit date/time, quoted total, clinic/dentist names, and service names.

Dates use Asia/Manila, today through 90 days ahead. Slots start every 15 minutes within a saved shift, fit the full treatment duration, and require 15 minutes of lead time. Pending, accepted, and confirmed reservations block overlapping times for the same dentist. The final check and inserts occur in one transaction under a clinic row lock shared with setup/review writes.

Dentist creates/updates accept optional serviceIds: up to 100 unique own-clinic service UUIDs. Omitting the field preserves existing assignments on updates; an empty array removes all assignments. Public booking uses active services and active dentists only.

The clinic review body uses decision: "accepted" or decision: "declined" and notes (string, up to 2,000 characters). Declining requires nonempty notes. Acceptance rechecks future time, active assignments, working hours, and conflicts. Reviewer/time/notes are saved. The response includes pendingAppointments for the workspace count. A stale decision returns 409.

Owner clinic sessions must supply clinicId on every clinic-tool read/write. Ordinary staff cannot use a clinic selector. Administrator portal routes and patient/clinic roles remain separate.

Database relationships link clinics to their owners, dentists/services to clinics, and appointments to patients and clinics. The API uses the session's account identity for private data rather than trusting a patient or clinic identifier supplied by the browser.

Account protection

Passwords are hashed with bcrypt at cost 12. They are not stored as readable passwords. Sign-in issues a random 256-bit opaque session token; only its SHA-256 hash is stored in the database. The token is sent in a protected browser cookie and checked against a valid database session on private requests.

Sessions are bound to the account's role. Password-hash or role changes revoke existing sessions through a database trigger. Re-login rotates the presented browser session, logout revokes it, and expiration is enforced on the server. Administrator sessions last one hour; patient/clinic sessions last eight hours.

Production uses separate public and administrator host-only cookies with Secure, HttpOnly, and SameSite=Strict. The __Host- cookie prefix, a root path, and the absence of a Domain attribute limit cookie scope. Cookies are not isolated by port alone; separate hostnames and cookie names provide administrator session separation.

Server and browser controls

The APIs validate inputs, enforce roles and clinic approval, parameterize data queries, check request origins, and reject unsupported portal endpoints. Nginx sends content-type, framing, referrer, permissions, and content-security headers. Private workspace and session responses are not cached.

API processes run as a non-root account with a read-only container filesystem, temporary storage, removed Linux capabilities, and no privilege escalation. PostgreSQL uses an internal Docker network. The production configuration publishes website ports 3003 and 3005, not direct API/database ports.

Production releases and five saved website versions

The production release manager keeps the five newest saved production versions. Each version contains the exact running application/container images, a PostgreSQL database backup, the running service configuration, and integrity checksums. Snapshots are private under .local/production-releases/. This directory is ignored by Git and restricted to the operator. Saved configuration and database files contain private information. Keep this folder off public web hosting.

Normal update workflow

  1. Make changes and rebuild the development preview using the operator’s separate development setup.
  2. Review the affected website behavior on phones and desktop and complete the relevant tests.
  3. Commit the tested source. Do not add untested changes between review and release.
  4. Deploy using the release manager, describing the actual website feature or fix:
cd /home/dentabook
python3 scripts/releases.py deploy --note "Patients can now filter clinics by treatment."

The example note illustrates the required wording; use the change actually implemented and tested. The command builds production images, saves the currently running website and database, verifies that saved copy, deploys the application services, and checks the website pages and APIs. The running production database container is retained. Any new application migrations still run on API startup.

Use this command instead of a direct docker compose build / up when releasing production so version retention and release records are applied. Development rebuilds remain separate and do not create production versions.

Five-version retention

Completed operations keep at most five saved restore points, ordered by their saved sequence. When a sixth complete copy exists, the oldest saved copy is removed. Its private archive and owned restore-image tags are removed; Docker retains any image still required by an existing container. Unrelated images, development services, production data volumes, and older manually made backups are not globally pruned.

No old version is removed to make room before the new recovery copy has completed successfully. A failed build or backup leaves the older saved versions intact. If a deployment or rollback fails after its recovery copy is verified, that newest copy is kept and the normal five-version limit still applies. Failed releases are not added to the website-update history. A sixth folder can exist temporarily while a release operation is running.

Available disk space is checked before saving. A full disk, export failure, invalid database dump, or invalid restore configuration stops the operation. Only one save/deploy/rollback operation can run at a time. Use the release manager for all production releases; simultaneous manual Docker operations are outside that lock.

List or save a version

python3 scripts/releases.py list
python3 scripts/releases.py save --note "Current clinic directory, patient accounts, and clinic review."

The list shows the exact version IDs needed for rollback, saved dates, and descriptions. A manual save creates a restore point without updating the live website and applies the same five-version limit. The version contains the website actually running at capture time, even when newer source exists in the working folder.

Restore a previous website version

Choose an exact ID from the list:

python3 scripts/releases.py rollback VERSION_ID --note "Restored working patient sign-in."

The command verifies the saved checksums, saves a rescue copy of the current installation, loads the saved images, restores the application services, and checks the website. It can capture an unhealthy application before rollback as long as the production database remains healthy.

Rollback preserves the current database. It does not erase appointments or restore older customer records. Before rolling back across a schema migration, check that the earlier application supports the current database schema. If it does not, use a forward fix or plan a separate, deliberate database recovery. A database restore can discard records created after the backup and is not automated by this command. The saved custom-format dump is available for an operator's recovery procedure.

The saved application images are loaded directly; rollback does not rebuild old source against newer packages. Existing production networks and data volumes are reused. Production configuration can contain passwords, so never copy the saved configuration into a public repository.
