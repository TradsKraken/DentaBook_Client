Project guide

Purpose

DentaBook brings clinic information, treatment information, and account access into one website. A visitor can compare available clinic information and understand published treatment prices before contacting a clinic.

The longer-term product includes appointment requests, clinic review of those requests, deposits, appointment tracking, and completed-visit feedback. Those later steps are listed separately in the development plan because they are not available in the current release.

Who uses the website

PersonWhat the current release allows
VisitorBrowse clinics and treatments, view public profiles, search, and estimate costs without an account
PatientRegister, sign in, view account details, and view appointments already linked to that account
Clinic representativeRegister a clinic, check review status, read review notes, and access the approved-clinic workspace
Platform administratorReview clinic submissions and approve or reject pending registrations

Each account is assigned a role. Registering as a patient cannot create a clinic or administrator account. Clinics appear publicly only after administrator approval. A clinic representative cannot enter the administrator workspace.

What a visitor sees

The homepage introduces the service and provides access to clinic discovery, treatment information, the calculator, and patient account pages. Clinic listings come from approved records saved in the database. The site shows a clear empty message when no clinics have been published, and a separate error message if information cannot be loaded.

The calculator uses a selected clinic's saved service prices. It does not make a reservation, accept money, or guarantee a final treatment bill. The clinic confirms the treatment and final cost directly with the patient.

Current delivery boundaries

This release supports discovery and account administration. A new clinic can register and be approved, but editing clinic descriptions, dentist records, prices, and schedules through the clinic dashboard is a later increment. Until that increment is delivered, an authorized operator must arrange data updates through a controlled maintenance process.

Patient appointment pages can display existing account-linked records. The website does not yet create new appointment requests or available time slots. A signed-in patient sees a clear notice where online booking is unavailable.

Design approach

The interface uses DentaBook's supplied logo and a blue-and-white theme. Layouts begin with narrow phone screens, with additional arrangements for tablets and desktop computers. Forms stack vertically on phones. Form text is at least 16px, and buttons and navigation actions are designed for touch.

Operational information is presented as loading, empty, error, or unavailable states as appropriate. The application does not invent clinics, ratings, prices, or successful appointment confirmations.

What this handoff contains

The source code, database initialization and migrations, configuration templates, automated tests, asset notices, and documentation are included. Live data, passwords, account recovery secrets, certificates, and private hosting credentials are transferred separately through the operator's agreed access process.

Use the user guide for step-by-step tasks and the development plan to review the remaining scope.

User guide

Browsing without an account

  1. Open https://dentabook.forgroup.space.
  2. Choose Find a clinic to open the directory.
  3. Search by the clinic, service, dentist, or location information available in the saved records.
  4. Open a clinic to view its public contact details, active services, and active dentist information.
  5. Use Cost calculator to select a clinic and its published treatments.
  6. Contact the clinic to confirm suitability, availability, and the final price.

If no clinics are listed, approved records have not been published yet. If an error message appears, use the retry action. An empty directory is not the same as a connection error.

Creating a patient account

  1. Open Patient registration at /patient/register.
  2. Enter your name, email address, phone number, and password.
  3. Confirm the same password and submit the form.
  4. After the account-ready message, continue to patient sign-in.
  5. Sign in with the email address and password you registered.

Passwords must contain at least 12 characters and no more than 72 UTF-8 bytes. Some symbols use more than one byte; an ordinary longer passphrase can meet the minimum without using complex symbols.

Patient registration does not grant clinic or administrator access. Password recovery and email verification are not yet implemented. If you forget your password, contact the designated website operator; there is no self-service reset link in this release.

Using patient pages

My account shows the signed-in patient's saved information. My appointments shows appointments already associated with that account, or an empty message when none exist. Other patients' information is not available through these pages.

Opening a personal page while signed out leads to patient sign-in. After a successful sign-in, the website returns to the requested patient page. Online booking submission remains unavailable; signing in does not create an appointment.

Registering a clinic

  1. Open /clinic/register on the main website.
  2. Enter the authorized account holder's name, account email, and password.
  3. Enter the clinic's name, address, public phone, public email, and registration or license reference.
  4. Confirm that you are authorized to register and manage the clinic.
  5. Submit the registration.
  6. Sign in at /clinic/sign-in to check the result.

The account email is used for sign-in. The public clinic email is contact information intended for the clinic's public listing. Submitting a registration does not automatically publish the clinic or approve its credentials.

Clinic review results

StatusMeaning and next step
Pending reviewAn administrator has not yet approved or rejected the submission
ApprovedThe clinic can appear in the public directory and the owner can access its workspace
RejectedThe clinic remains unpublished; read the review notes and contact the operator about correction
SuspendedThe clinic workspace is unavailable while the suspension remains in place

The approved-clinic workspace displays saved clinic information and available database counts. Editing services, dentist information, schedules, and appointments is planned work. The current administrator interface approves or rejects pending clinics; it does not provide a complete suspension-management workflow.

Reviewing clinics as an administrator

  1. Open https://dentabook-admin.forgroup.space/admin/sign-in.
  2. Sign in with an administrator account provided through the operator setup process.
  3. Open the list of pending clinic registrations.
  4. Review the submitted details and reference information using the organization's review procedure.
  5. Choose approve or reject and complete the confirmation step.
  6. Provide a reason when rejecting a registration.
  7. Confirm that the updated result appears in the appropriate list.

A review records the decision, reviewer, time, and notes. Approval is an application publishing decision; the software does not independently verify a professional license. There is no public administrator registration or default administrator password.

Signing out and switching accounts

Choose Sign out before using a shared device or changing between patient and clinic accounts. Those two roles share the main website's browser session. Administrator access has its own hostname and session. Administrator sessions last one hour; patient and clinic sessions last eight hours unless revoked earlier.

If sign-in expires, sign in again. Changing a password or account role through an authorized maintenance process revokes existing sessions.

Technical overview

How the website is organized

DentaBook has three application layers: the browser interface, the server API, and the database. Production runs the API in two processes so administrator access is separated from the public and clinic site.

The browser presents forms and pages. The API validates submitted information and enforces account permissions. PostgreSQL stores the records. A browser cannot gain administrator access by changing a page link, form value, or request header.

How information moves through the system

When a visitor opens the clinic directory, the browser requests /api/clinics. The API reads approved clinics and their active public services and dentist information. It returns data for the interface to display. If the query fails, the page shows a loading error rather than an invented clinic listing.

When a patient or clinic representative signs in, the server checks the password hash and required role. It creates a random session token, stores only its hash, and places the token in a protected browser cookie. Each private request is checked against the saved session. Authentication uses database-backed opaque sessions; it does not use JWT tokens.

When an administrator reviews a registration, the administrator API checks the session and role before changing a pending clinic's status. The change is saved with the reviewer and review information. Public directory queries only include approved clinics.

Implementation approach

The application is organized into incremental capabilities: public discovery, account registration and permissions, clinic review, production separation, and testing. Interfaces use actual API data and explicit states for incomplete operations. Database changes are applied through versioned migration files rather than relying on manual changes to every installation.

The next increments extend clinic data management and scheduling before enabling appointment submission. The development plan explains this order and its acceptance criteria.

Setup and deployment

This guide is for the person responsible for hosting. Routine users only need a browser and the website addresses in the user guide.

Requirements

Use a server with Docker Engine and Docker Compose 2.24.4 or newer. Production requires the public and administrator hostnames to point to a reverse proxy, a valid certificate for each hostname, and HTTPS. Node.js 22 is needed on a workstation only when running development tools outside Docker.

Run a test installation on a separate machine from the live stack. The supplied container names are fixed; another copy on the same machine will conflict with the running containers unless the operator deliberately changes the configuration.

Local evaluation

  1. Copy .env.example to .env in the project root.
  2. Replace the database password placeholder with a newly generated random password.
  3. Set NODE_ENV=development and CLIENT_URL=http://localhost:3000.
  4. Keep the production COMPOSE_FILE setting disabled for a combined local preview.
  5. Confirm that ports 3000, 5000, and the chosen database diagnostic port are unused.
  6. Run:
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
curl --fail http://localhost:3000/api/health

Open http://localhost:3000. Local patient, clinic, and administrator routes share that origin, with server-enforced roles. Local HTTP is for controlled evaluation; production uses HTTPS.

Production configuration

On the intended production server, copy .env.production.example to .env. Preserve an existing production .env when updating a live installation. Supply a unique database password before first startup. On Linux, restrict the file with chmod 600 .env.

The database initializes a new persistent volume on first startup. API startup applies pending migrations. An existing volume is reused on later deployments. Changing an environment password does not automatically change the password inside an existing database.

Production contains four services: the website, the public/clinic API, the administrator API, and PostgreSQL. The APIs and database have no published host ports. The website exposes ports 3003 and 3005 for the upstream reverse proxy.

First administrator

An operator creates the first real administrator interactively:

docker compose exec api npm run create-admin

Enter the intended person's name, email, and a private password. There are no default administrator credentials. Transfer access through the agreed private process, not through a source-code file or this documentation.

Verify the installation

curl --fail https://dentabook.forgroup.space/api/health
curl --fail https://dentabook-admin.forgroup.space/api/health
curl --fail --location --head https://dentabook-admin.forgroup.space/
curl --fail --head https://dentabook.forgroup.space/clinic/sign-in

Both health responses should report healthy and a connected database. Administrator pages must return 404 on the public host; patient and clinic pages must return 404 on the administrator host. Then run the acceptance checks.

If the domains change, update the origins in .env, rebuild the client, recreate the API services, and update DNS/certificates. Public and clinic links are configured during the website build.

Operations manual

Routine checks

Use the correct project directory and production .env. Check docker compose ps, both HTTPS health endpoints, certificate renewal, available disk space, and the most recent verified backup. Agree an appropriate check schedule and responsible operator before relying on the system for daily operations.

docker compose ps
docker compose logs --tail=100 api admin_api client db

Logs can contain operational or account-related information. Share only the relevant, redacted excerpt when requesting support.

Backing up the database

The persistent Docker volume keeps records when containers are replaced. It is not a separate backup. Create a private backup before every release or database maintenance operation, and on the schedule agreed with the project owner.

From the project root on a Linux host:

mkdir -p .local/backups
chmod 700 .local/backups
umask 077
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > ".local/backups/dentabook-$(date +%Y%m%d-%H%M%S).sql"

Keep a protected copy outside the production server. Test recovery periodically in an isolated environment. Store the configuration and access needed for recovery separately from the database backup. This release does not configure scheduled backups, backup encryption, or retention automatically.

Recovery procedure

  1. Identify the last verified backup and the application version it belongs to.
  2. Prepare an isolated PostgreSQL 16 database with the required database role and extension permissions.
  3. Restore the SQL backup into a new, empty database using an authorized database operator's connection. A command such as psql --set ON_ERROR_STOP=1 --dbname "$RESTORE_DATABASE_URL" --file backup.sql must target that recovery database, not the live one.
  4. Check account and clinic record counts, session behavior, directory data, and the relevant application workflows against the restored database.
  5. Agree the production recovery window and data cutover before reconnecting the live application.
  6. Repeat the health and acceptance checks after cutover.

The backup format is plain SQL. Restoring it into an already initialized database may conflict with existing tables or records; prepare an empty recovery database and stop on errors. Do not attempt a production restore by trial and error.

Installing a new release

Confirm that the release has passed the agreed tests and read its release notes. Back up the database and retain the previous release and its configuration. For a clean client repository checkout, obtain the approved release using the agreed branch or tag, then run:

docker compose config --quiet
docker compose build
docker compose up -d --wait
docker compose exec -T client nginx -c /etc/nginx/portals/nginx.conf -t
docker compose exec -T client nginx -c /etc/nginx/portals/nginx.conf -s reload

Verify the two HTTPS health endpoints and the user journeys. Database migrations run at startup and may require a recovery plan beyond restarting an old image. The current project has no general automatic migration-down command.

Never use docker compose down -v for a routine update: it deletes the named database volume. docker compose down stops the stack without deleting that named volume. Keep production configuration independent from local testing.

API reference

This appendix is for developers and operators. Browser users should use the normal website forms.

Hosts and request rules

Public and clinic requests use https://dentabook.forgroup.space/api. Administrator requests use https://dentabook-admin.forgroup.space/api. Browser requests stay on the current host and use its session cookie.

State-changing requests use JSON, Content-Type: application/json, and X-DentaBook-Request: 1. The server rejects mismatched browser origins and cross-site request metadata. A valid session is still required where shown below. The configured API process rejects routes belonging to another production area with 404.

Clinic registration accepts ownerName, email, password, clinicName, address, phone, contactEmail, registrationReference, and consent: true. Client-side password confirmation is not a stored field. Unknown role/status fields cannot select elevated privileges.

Administrator endpoints

The administrator host also provides /health, the public clinic read endpoints, and its own /auth/me and /auth/logout session operations.

The review body uses decision: "approved" or decision: "rejected", with optional notes. Rejection requires nonempty notes. Notes are limited to 2,000 characters. A previously reviewed registration returns a conflict instead of being reviewed again as pending.

Successful endpoints return JSON, except logout returns HTTP 204. Sign-in sets a protected cookie; it does not return a bearer token in the response body. Private session/workspace responses use Cache-Control: no-store.

Database relationships link clinics to their owners, dentists/services to clinics, and appointments to patients and clinics. The API uses the session's account identity for private data rather than trusting a patient or clinic identifier supplied by the browser.

Account protection

Passwords are hashed with bcrypt at cost 12. They are not stored as readable passwords. Sign-in issues a random 256-bit opaque session token; only its SHA-256 hash is stored in the database. The token is sent in a protected browser cookie and checked against a valid database session on private requests.

Sessions are bound to the account's role. Password-hash or role changes revoke existing sessions through a database trigger. Re-login rotates the presented browser session, logout revokes it, and expiration is enforced on the server. Administrator sessions last one hour; patient/clinic sessions last eight hours.

Production uses separate public and administrator host-only cookies with Secure, HttpOnly, and SameSite=Strict. The __Host- cookie prefix, a root path, and the absence of a Domain attribute limit cookie scope. Cookies are not isolated by port alone; separate hostnames and cookie names provide administrator session separation.

Server and browser controls

The APIs validate inputs, enforce roles and clinic approval, parameterize data queries, check request origins, and reject unsupported portal endpoints. Nginx sends content-type, framing, referrer, permissions, and content-security headers. Private workspace and session responses are not cached.

API processes run as a non-root account with a read-only container filesystem, temporary storage, removed Linux capabilities, and no privilege escalation. PostgreSQL uses an internal Docker network. The production configuration publishes website ports 3003 and 3005, not direct API/database ports.

Limits and continuing work

HTTPS protects browser-to-proxy traffic when DNS, certificates, and redirects are configured correctly. The proxy-to-application LAN hop and application-to-database Docker hop are not encrypted by the current setup. Database-volume and backup encryption are not automatically configured.

MFA, self-service password recovery, email verification, durable shared request throttling, and a full security audit trail are future work. Current request limits are stored in each API process's memory and reset with that process. The project has automated access-control tests; it has not undergone an independent penetration assessment.

Operators with host or database access can access stored records. Control access to hosting, database backups, source repositories, and configuration separately. Agree data retention, account support, and recovery responsibilities with the project owner before collecting additional information in later features.

Configuration and backups

Actual database passwords belong in a private .env, not in source control. Keep backup files private and outside release archives. Preserve included dependency and asset notices. Transfer access through the agreed private process and rotate credentials when access responsibility changes.
